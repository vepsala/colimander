Colimander

Per-project dev VMs with a credential firewall, so you can let an agent off the leash without handing it your real tokens.

The problem

I work on 3–5 projects in parallel on an M3 with 36 GB of RAM. That isn't enough to keep five fully-provisioned dev environments hot — language servers, Postgres, browsers, agent VMs all stacked. So in practice: 1–2 "safe" environments, and unsafe shortcuts on the rest.

Agents like Claude Code thrive when they can see the whole environment — real language servers, real databases, real tools. The cloud-sandbox version is always a step behind. The cost is that local-first agentic development has become synonymous with the agent has your real GitHub token, your real DB password, your real filesystem.

Two halves of the chore:

  • Lifecycle ergonomics — spin up, swap between, and tear down environments without losing track of what's where.
  • Safety without overhead — run claude --dangerously-skip-permissions anywhere without holding your breath.

How it works

Each project is a Colima profile — its own VM, disk, and Docker context, with no host bind-mount. Real secrets stay in macOS Keychain on the host. The VM gets local-only handles, and a host daemon brokers every sensitive connection, swapping in the real credential only for operations its policy allows.

One VM per project

Each profile is a Colima VM with its own disk and Docker context, templated from a colima.yaml Colimander owns. Create, start, stop, destroy are thin wrappers.

No host bind-mount

Project files live only inside the VM. You edit over SSH from Zed / VS Code / Cursor / JetBrains. If the VM gets popped and drops a binary, the host never sees it.

No port collisions

Every profile gets a routable IP and a .local hostname in /etc/hosts, so myproj.local:3000 and other.local:3000 both work at once.

Policy the platform can't express

Allow writes to two repos, allow repo creation, deny DELETE /repos/*, deny renames. Finer than a fine-grained PAT, without installing an App per org.

Aggressive defaults

Deletion, webhook tampering, SSH/GPG key changes, secret deletion, org settings, role escalation — denied. Reads and benign writes pass.

Every redemption logged

colimander logs is a live TUI over the broker audit log, filterable by profile, surface, and action — including auth failures.

Why a broker beats a firewall

Most agent-sandbox setups need egress allow-lists, DNS filtering, iptables rules — all trying to stop credential exfiltration at the network layer. If the credential the agent holds doesn't work off your machine in the first place, you don't need that ceremony. The VM can have wide network access; the interesting things are gated at the broker.

That's what makes --dangerously-skip-permissions defensible: not because the agent is well-behaved, but because the worst it can do is bounded by policy — and rotating a secret changes nothing inside the VM.

Status

v0, and honest about it: the lifecycle CLI and the credential broker work and are validated by hand on macOS with real VM boots. Several conveniences from the design doc are still unwritten.

Working

  • setup wizard, create, start, stop, destroy
  • ssh, status, ls, ports, hosts-sync
  • broker — git + GitHub API proxy with allow/deny policy
  • policy, tokens — fly.io and Doppler surfaces
  • logs — live TUI over the audit log
  • packages — Claude Code, OpenCode, Postgres, Node via mise
  • Guardrail: mutating commands refuse unmanaged profiles

Not built yet

  • A sibling project for remote VPS environments

Try it

git clone https://github.com/vepsala/colimander
cd colimander
go build -o colimander .

./colimander setup          # wizard: deps, name, specs, optional import
./colimander broker start   # host-side credential proxy
./colimander ls

Requires macOS with Colima and Go. The README carries the full design rationale, and docs/external-brokers.md covers the fly.io and Doppler surfaces.

Threat model

Defends against

  • Agent writing to the host filesystem — no bind-mount
  • Credential exfiltration — only inert handles are in the VM
  • Cross-project credential reuse — identity is per profile
  • "I forgot prod is still loaded" — TTLs on borrowed secrets

Does not defend against

  • A kernel exploit that escapes the VM
  • You typing the real secret into the VM yourself
  • macOS itself being compromised — Keychain is the trust root

Prior art

  • Trail of Bits — claude-code-devcontainer: closest existing thing; solid filesystem boundary, no credential broker.
  • Anthropic — Securely deploying AI agents: gestures at the proxy pattern.
  • Patrick McCanna — Limiting coding-agent access to secrets: likewise.
  • Lima and Colima: the foundation this sits on.
